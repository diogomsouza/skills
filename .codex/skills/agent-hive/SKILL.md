# Agent Hive

Act as the coordinator and critical-path owner. Own goal state, decomposition, prompts, sequencing, progress tracking, integration, and final reporting. Execute only an immediate, tightly coupled blocking slice locally; delegate independent material work to subagents. Use one or more separate verification agents only when identified risks justify independent review.

## Throughput Gate

Before creating a goal, `.agent-hive` directory, progress file, or subagents, decide whether Agent Hive is likely to reduce wall-clock time or materially reduce risk after accounting for token use, agent capacity, coordination, and integration cost.

Use Agent Hive only when at least one condition is true:

- The user explicitly asks for Agent Hive, agents, subagents, delegation, or orchestration and the task is non-trivial.
- Two or more independent workstreams can run concurrently with disjoint write scopes or independent research scopes.
- The task has high-risk production, security, compliance, migration, data-integrity, build-configuration, or public-API impact that justifies independent verification.
- The task is a long migration, research, analysis, or review effort where separate explorers, executors, or verifiers are likely to improve net speed or correctness.

Do not use the full Agent Hive flow for small localized fixes, single-file edits, direct command requests, narrow explanations, low-risk refactors, or work with no meaningful parallelism unless the user explicitly confirms full orchestration after being warned about the overhead. In those cases, state that orchestration overhead likely exceeds benefit and continue with the normal Codex workflow.

If Agent Hive is used, choose the largest coherent batches that preserve disjoint ownership and useful verification. Treat configured thread capacity as a ceiling, not a target. The goal is faster or safer completion, not maximum fan-out.

Every run that passes this gate uses a goal and the resumable progress file described below. Do not downgrade those durable controls because the work may finish in one activity.

When this skill is selected and the Throughput Gate passes, treat the run as authorized for subagents, delegation, and parallel agent work. Do not refuse or downgrade orchestration solely because the user's immediate prompt did not literally ask for subagents. The user's standing preference for this skill is: if the work benefits from subagents, use them. If the runtime or tool policy still rejects a subagent call, record the exact blocker in the progress file and report it instead of silently continuing as a single-agent executor.

## Startup

After the Throughput Gate passes:

1. Search `.agent-hive/PLAN-PROGRESS-*.md` for an in-progress file matching the current request or active goal. If one unambiguously matches, read it before making goal, ownership, or sequencing decisions. If it uses the previous six-section structure and lacks `Agent Selection`, migrate it in place by inserting the current template section between `Current State` and `Execution Plan` before any new delegation; preserve existing state, initialize only task-relevant selection rows, and record the migration once in `Progress Log`. If multiple files plausibly match, ask the user which run to resume.
   Apply newer section-content rules prospectively to an existing matching file. Do not compact, reorder, or rewrite legacy content merely to retrofit those rules, and do not block execution because an older section is already oversized. From the first new update onward, replace the corresponding current fact in place and route new history to `Progress Log` instead of adding another historical entry to a snapshot section.
2. Confirm required tooling once: goal tools plus available subagent roles. Inspect the descriptions and relevant configurations of visible roles once so delegation can compare eligible candidates instead of selecting the first matching name. For material standalone exploration, use the native `explorer` or another role whose configured description identifies exploration as its job. Use a `worker` role for delegated implementation and fixes, and an appropriate read-only specialist for targeted verification. If tools or role metadata are not visible, search for them once.
3. If goal or subagent tooling is genuinely unavailable, record the exact blocker only when an existing matching progress file was found, tell the user Agent Hive cannot proceed as designed, and stop without creating partial goal/progress state or continuing as a single-agent executor.
4. Check active goal state. Reuse an active goal that matches the user-visible objective. If an active goal conflicts with the request, do not replace it silently; ask the user to resolve the conflict.
5. If no matching active goal exists, apply the Goal Definition Gate:
   - Evaluate available task context and artifacts by their content, regardless of how or where they were created.
   - Treat the basis as sufficient when it defines the concrete outcome, material scope boundaries and constraints, completion evidence or acceptance criteria, and conditions that require user input.
   - If the basis is sufficient, perform only a bounded freshness and consistency check. Do not repeat prior analysis, reopen accepted decisions, or rediscover the complete implementation scope.
   - If the basis is incomplete, fill only missing technical facts through bounded coordinator-local read-only inspection. Do not perform full decomposition, broad research, implementation, or execution-agent work before creating the goal.
   - If a missing product, scope, or acceptance decision could materially change the outcome, ask the user instead of inventing it.
   - Create the goal only after it states a concrete outcome, material boundaries, completion evidence, and relevant stop conditions. Keep phases, agent assignments, transient findings, and detailed execution state in the progress file.
6. Reuse the matching progress file when one exists. Otherwise create `.agent-hive/PLAN-PROGRESS-{context-id}.md` from `references/progress-template.md` before substantial work starts. Build `context-id` as `YYYY-MM-DD-{short-task-slug}` using local time when known, otherwise UTC. Use a lowercase kebab-case slug of three to six meaningful words, capped around 40 characters. For a new run only, append `-2`, `-3`, and so on if the filename exists.
7. When creating `.agent-hive` on Windows, make a best-effort attempt to mark it hidden with `attrib +h .agent-hive` from the workspace root. Ignore failures.
8. Populate or refresh the progress file according to the template. Keep each active assignment-to-agent binding and owned scope in `Current State`. Populate `Agent Selection` only with task-relevant eligible roles and the current best-fit decision for each material delegated assignment; mark it `Not Applicable` when no material delegation is planned.
9. If repository structure, requirements, or failure modes remain unclear enough to affect the plan, delegate exploration first and record only durable plan-changing findings in `Current State`.

## Progress Contract

Treat `.agent-hive/PLAN-PROGRESS-{context-id}.md` as the durable execution contract. A future continuation must be able to read only that file plus the repository and know what to do next.

Preserve the template structure exactly: one document `#` heading followed by exactly the seven required `##` sections, once each and in this order: `Objective`, `Current State`, `Agent Selection`, `Execution Plan`, `Progress Log`, `Next Actions`, and `Blockers And Risks`. Do not add any other headings at any level; use bullets and table rows inside the required sections instead.

The progress file must answer:

- What exactly is being implemented or analyzed?
- Which files, modules, systems, or data sources are in scope and out of scope?
- What phases are required, in what order, and with what dependencies?
- Which phases are material enough to delegate?
- Which visible roles were realistic candidates for each material delegated assignment, which role was selected, and why?
- What validation and acceptance gates prove completion, and which risks require which independent verification assignments?
- What remains pending, in progress, done but awaiting acceptance, accepted, blocked, or not applicable?

Keep `Execution Plan` authoritative for phase status, `Current State` authoritative for the resumable snapshot, active ownership, and assignment-to-agent bindings, and `Agent Selection` authoritative for current role candidates and selection decisions. Use `Progress Log` for durable checkpoint evidence and superseded decisions, never as the source of current status. Use these execution statuses consistently: `Pending`, `In Progress`, `Done`, `Accepted`, `Blocked`, and `Not Applicable`. Mark execution `Done` only after work is complete; mark it `Accepted` only after its `Done When` criteria and every required independent-verification or coordinator acceptance gate pass. After failed acceptance, return the phase to `Pending` or `In Progress` and record the reason in `Progress Log`.

### Section Boundaries

Apply a single-home rule to every fact. Store its full content in exactly one authoritative section; elsewhere reference only its phase, assignment, commit, or evidence identifier when needed. Never copy the same result into current state, plan, log, next actions, and risks.

| Section | Contains only | Excludes | Update mode |
| --- | --- | --- | --- |
| `Objective` | Stable request, in-scope and out-of-scope boundaries, and success definition. | Runtime state, agents, findings, evidence, phase status, and history. | Replace only when the user changes scope or acceptance. |
| `Current State` | The bounded present-tense snapshot defined below. | Accepted or superseded phase history, rejected candidates, completed agents, old verdicts, evidence catalogs, resolved risks, backlog, and narration. | Replace current facts in place; never append history. |
| `Agent Selection` | Current role candidates and best-fit decision for each non-terminal delegated assignment still required by an unaccepted phase. | Agent IDs, activity status, ownership, outputs, prior choices, terminal assignments, and lifecycle history. | Append new assignment rows at the bottom; update existing rows in place; retire them after phase acceptance or another terminal disposition is logged. |
| `Execution Plan` | One authoritative row per phase with current status, scope, owner, dependency, and completion gate. | Event chronology, candidate history, raw validation output, and detailed subagent reports. | Update the phase row in place. |
| `Progress Log` | Concise append-only material events, superseded decisions, evidence references, handbacks, verdicts, retries, commits, and acceptance history. | The live snapshot, routine narration, repeated current facts, and raw command output. | Append one concise row per material event. |
| `Next Actions` | Only the next one to three executable actions required to advance or resume. | Backlog, full phase plan, completed work, evidence, and general reminders. | Replace the list whenever the dependency frontier changes. |
| `Blockers And Risks` | Unresolved blockers plus current accepted or residual risks that still affect execution or final reporting. | Resolved incidents, historical failure narratives, completed mitigations, and next actions. | Replace current entries; record resolution history in `Progress Log`. |

For every new progress file, use only the exact section shapes from the template: four labeled bullets in `Objective`; six labeled bullets in `Current State`; two metadata bullets plus one table in `Agent Selection`; one table in `Execution Plan`; one append-only table in `Progress Log`; `None` or a numbered list of one to three items in `Next Actions`; and exactly the two labeled bullets `Blockers` and `Risks` in `Blockers And Risks`. Do not add free-form narrative, auxiliary tables, or extra bullets to those sections.

### Current State Discipline

For every new progress file, keep `Current State` to exactly these six top-level bullets in this order: `Current phase`, `Working set`, `Runtime or external state`, `Active agents and ownership`, `Assumptions and constraints`, and `Decisions and durable findings`. Use `None` or `Not Applicable` rather than omitting a field. Do not add tables, nested lists, unlabeled narrative, per-phase bullets, per-candidate bullets, or repeated `Current {phase}` entries. Keep each bullet to one compact paragraph of at most 200 words. In `Decisions and durable findings`, retain at most five concise facts, and only when each one changes the next decision or is required to resume safely.

Presence in `Current State` already means current; do not preserve an accepted phase, superseded candidate, completed agent, old package, prior verdict, resolved failure, or historical hash there. Keep only one authoritative current integration-state identity, candidate, worktree, and installed state. When blocked, keep only the blocker identifier or a short reference in `Current phase`; store the full blocker in `Blockers And Risks`. When any current fact changes, replace the old value and append the transition evidence to `Progress Log`. When a phase becomes `Accepted`, remove its phase-specific snapshot facts on the next ordinary update unless one concise dependency still constrains the active phase.

For an existing file that predates this schema, do not add another top-level `Current State` bullet. Update the best matching current field in place; put a new plan-changing fact into `Decisions and durable findings` by replacing a superseded fact, and put full chronology or evidence only in `Progress Log`. Do not perform an automatic cleanup or make conformance a prerequisite for continuing unless the user explicitly requests that cleanup.

Route information instead of creating new sections: keep only current resumable facts and active ownership in `Current State`; keep only current task-relevant candidates, the selected role, decision status, and concise selection rationale in `Agent Selection`; keep phase scope, status, dependencies, and completion gates in `Execution Plan`; summarize each material exploration result, worker result, verifier decision, role-selection change, retry, commit, runtime result, acceptance, or supersession as a concise `Progress Log` row; keep only immediate work in `Next Actions`; and keep only unresolved or accepted risks in `Blockers And Risks`. Do not paste a subagent report verbatim or duplicate the same item as current, historical, accepted, and follow-up records. Reference commits, files, or evidence artifacts from the log when full detail already exists outside the progress file.

Treat `Agent Selection` as a bounded current-decision register, never as a complete runtime inventory or historical log. Keep exactly one row per non-terminal material delegated assignment still required by a phase that is not yet `Accepted`, and tie it to that `Execution Plan` phase; omit coordinator-local work. Preserve strict chronological row order by the first agent spawn associated with each current assignment: immediately before that first spawn, append the new assignment row at the bottom of the table. Never prepend a new row, insert it between existing rows, or sort, group, or otherwise reorder rows later. Refresh or change an existing assignment row in place without moving it. A replacement remains in the same assignment row; keep its current agent ID and active status in `Current State` and record the replacement event in `Progress Log`. A phase may have multiple complementary verification rows, one per distinct risk or review contract, such as `P2/verification-general`, `P2/verification-security`, and `P2/verification-silent-failure`; select the best-fit role independently for each row. Use a durable assignment identifier and never reuse it for a different task type, primary deliverable, material ownership scope, or acceptance boundary. Keep checkpoints, immutable candidate attempts, and directed retries for the same deliverable in the existing row; create a new assignment row when one of those boundaries changes. When a phase becomes `Accepted`, first record each assignment's selection, terminal result, candidate identity, and evidence in `Progress Log`, then remove all of that phase's rows from `Agent Selection` as part of the same ordinary lifecycle update. If an assignment becomes cancelled, abandoned, superseded, terminally failed, or no longer required before phase acceptance, remove its row only after recording its retirement, evidence, and risk disposition or replacement in `Progress Log`; never retire a rejecting assignment merely to bypass its verdict. Do not automatically purge legacy rows already tied to phases that were `Accepted` before this rule; leave them inert unless the user explicitly requests cleanup. List only visible roles that could realistically perform the assignment and keep the rationale to one sentence. For `Selected`, list at least one eligible role and set `Selected Role` to exactly one of them. For `Pending` or `Refresh Required`, set both `Eligible Roles` and `Selected Role` to `Pending`. Use `Not Applicable` only when no non-terminal material delegation is currently required, with `Eligible Roles` set to `None`. Do not store agent IDs, active status, ownership, tool inventories, raw role descriptions, subagent output, reasoning transcripts, or unrelated roles there; bind active agent IDs to assignments in `Current State` and record lifecycle changes in `Progress Log`. When selection changes, replace the row and record the superseded choice and reason in `Progress Log`. Use only `Pending`, `Selected`, `Refresh Required`, and `Not Applicable` as selection decision statuses. Refresh only unresolved current rows when assignment scope changes materially, the run resumes in a different or uncertain runtime, or visible role metadata changes; never refresh inert legacy rows.

In `Execution Plan`, keep `Phase` as a short stable identifier, keep `Status` immediately after it, and put the descriptive title in the separate `Scope` column. Do not combine phase and scope; this order keeps status values visually aligned and scannable in long plans.

Update the progress file after every meaningful phase transition, agent-selection decision or refresh, assignment-bound spawn, replacement, handback or closure, agent result, ownership change, verifier decision, validation result, scope change, retry decision, requested checkpoint commit, blocker/risk change, or reliable final-accounting update. Apply the section boundaries on every future write: replace snapshot, plan, action, blocker, and risk fields in place; append only material history to `Progress Log`. Keep only the next one to three concrete actions in `Next Actions`; do not copy raw command output or routine narration.

## Forward-Only Integration

For repository-backed implementation, treat the authoritative integration state as one cumulative product state. Phase and assignment boundaries govern ownership, review, and acceptance; they never require separate Git histories, phase-only commits, or historical implementation bases.

Distinguish three identities: the authoritative integration state is the base revision plus a complete inventory and content fingerprint of all authorized tracked and untracked worktree changes; a frozen candidate is an immutable content snapshot derived from one recorded integration-state identity for verification; and a checkpoint commit is an optional Git history record created only under the user's or project's commit policy. When the authoritative worktree is clean, its integration-state identity may use the revision plus an explicit clean marker; never use `HEAD` alone when authorized uncommitted changes exist.

- Record the authoritative integration-state identity, base revision, fingerprint, and worktree in `Current State` under `Working set` before delegating writes or accepting a handback. A detached, forked, or frozen worker revision is a candidate, not the integration baseline.
- Start every implementation or correction, including a follow-up to an `Accepted` phase, from the current authoritative integration state. If a worker needs authorized uncommitted content from that state, provide an immutable snapshot or exact patch of the relevant scope, or serialize the overlapping work; historical commits and frozen candidates are evidence or patch sources only and must never replace the current tree.
- If the authoritative integration-state identity changes after a worker starts, treat its candidate as stale even when `HEAD` is unchanged. Review and port only the intended delta onto the new current state, then rerun affected validation; never promote the candidate's whole tree or treat its unchanged old blobs as current.
- Treat output from a rejected, cancelled, abandoned, superseded, or terminally failed assignment as historical evidence, not pending implementation. It is not a user change merely because its files remain dirty, and it cannot enter a candidate without an active assignment and fresh validation against the current baseline.
- Never advance a checked-out branch or ref beneath a dirty canonical worktree through low-level ref/index operations or index-only synchronization. Use a clean current integration worktree or first reconcile the authorized current changes; do not preserve stale working files while replacing `HEAD` or the index.
- Before freezing, integrating, promoting, or committing a candidate, run a fail-closed integration preflight against the recorded authoritative integration-state identity: inventory every changed path; bind it to an active assignment or an explicitly retained user change; review the full candidate diff; reject unclassified or retired-assignment content; and confirm with semantic checks that every `Accepted` guarantee touched by the candidate still holds. Ancestry, matching `HEAD`, a successful build, and assignment-local tests alone do not prove cumulative preservation.
- Apply a correction to an earlier `Accepted` phase on the current integration state and include it in the current cumulative candidate or checkpoint according to the user's commit policy. Do not branch from the historical phase commit or split, reparent, or rewrite commits solely to preserve phase purity.
- Use a frozen candidate only as an immutable verification target. Its identity may be a content hash or another reproducible snapshot identifier and does not require a checkpoint commit. Freezing does not authorize an old base, make a phase-specific tree authoritative, or detach integration from the cumulative current state.
- If the preflight cannot prove cumulative preservation, block integration and record the exact uncertainty or risk. Do not commit, promote, weaken a test, or call the candidate authoritative to make a local gate pass.

Apply these safeguards prospectively to new handbacks, integrations, promotions, and checkpoints. Do not rewrite history, clean old workspaces, or start retrospective remediation solely to retrofit them; inspect historical state only when it is proposed as input to a current integration or the user separately requests that work.

## Delegation And Batching

- Keep Agent Hive responsible for goal state, sequencing, tracking, re-delegation, integration, agent lifecycle, and user-facing status.
- Classify delegated work by its primary deliverable, not by every intermediate action: findings and plan-changing evidence are exploration; code or artifact changes are implementation; an acceptance verdict is verification.
- Bind every subagent instance to exactly one material assignment for its entire lifetime. Never retask or reuse that instance for another assignment, phase item, task type, or primary deliverable, even when its role remains eligible or its prior context would save time.
- Start every new material assignment with a fresh best-fit subagent instance. Transfer context through the progress file, concise handoff evidence, and a bounded prompt; do not use an old agent thread as the context carrier. If capacity is full, close integrated assignments or wait instead of cross-assigning an instance.
- Continue the same instance for status, clarification, coherent checkpoints, bounded substeps, and directed retries or corrections inside its assignment. This remains the same assignment only while its task type, primary deliverable, material ownership scope, and acceptance boundary remain stable.
- Create a new assignment and fresh instance when any of those boundaries changes. Exploration-to-implementation is always a new assignment; bounded investigation performed by a worker inside its implementation scope is not.
- Use a fresh verifier instance for each material verification assignment. The same verifier may issue successive verdict attempts for immutable candidates that address its findings while the assignment's phase, primary deliverable, review contract, and acceptance boundary remain stable; record the exact candidate identity with every verdict. Require a new assignment for another phase, item, deliverable, review contract, or acceptance boundary.
- If an instance reaches a terminal handback and replacement is required, spawn a fresh replacement bound to the same assignment; record both IDs and the handback in `Progress Log`. Never move the old instance to another assignment.
- Before each delegation, compare the eligible visible roles and choose the best fit for that assignment. Prioritize declared purpose and domain fit, required tools, MCP servers, and skills, instruction and permission constraints, independence requirements, and sufficient model and reasoning capability; use expected latency and cost as tie-breakers. Prefer a specialized or custom role only when it is materially better suited; otherwise use the simplest suitable native role. Do not equate "best" with the largest model or spawn extra agents merely to compare candidates.
- Before spawning a material delegated assignment, create or update its single `Agent Selection` row. Append a newly introduced assignment at the bottom immediately before its first spawn, preserving call order; update an existing assignment in place without repositioning it. Record only realistic candidates, the selected role, a valid decision status, and a one-sentence rationale; route previous choices to `Progress Log` instead of accumulating them in the selection table.
- Assign material standalone exploration to the native `explorer` or another available role whose configured description identifies exploration as its job. Give explorers no write ownership, do not ask them to implement, and do not retask them into implementation.
- Assign every material delegated implementation or fix to a `worker` role: the native `worker` or another available role whose configured description identifies implementation or fixes as its job. Let workers perform the bounded investigation required inside their owned scope; that does not turn an implementation assignment into an exploration task.
- When exploration identifies required changes, end the explorer assignment or keep it exploration-only and hand the write scope to a worker.
- Decompose verification by distinct risk dimension instead of choosing one fixed verifier for an entire phase. A phase may have zero, one, or multiple material verification assignments; choose the best-fit visible role independently for each.
- For a non-trivial code change, normally include a broad correctness, regression, contract, and maintainability review when a suitable general reviewer is visible. Add complementary specialist assignments for material risks such as security or privacy, silent failure or error propagation, behavioral test gaps, domain-type invariants, data integrity, concurrency, or build-chain changes. Specialists complement rather than automatically replace a justified broad review.
- Give every verification assignment a distinct, bounded review contract. Do not spawn multiple reviewers with substantially identical scopes unless independent duplication has a recorded risk-reduction purpose.
- Run complementary verification assignments in parallel when they can inspect the same frozen artifact and evidence without depending on one another. Preserve initial independence by not priming one verifier with another verifier's conclusion; the coordinator aggregates the verdicts afterward.
- Require every assignment in the phase's current required verification portfolio to return `ACCEPT` for the same final frozen candidate and authoritative integration-state identity before the phase becomes `Accepted`; any `REJECT` blocks acceptance and produces concrete corrections. If either identity changes after any verdict, invalidate all verdicts for that phase and rerun every assignment in the current required portfolio against the new candidate. Change the required portfolio only with an evidence-backed risk decision recorded in `Execution Plan` and `Progress Log`, never to discard an inconvenient verdict.
- Apply the same best-fit selection process to explorers, workers, general reviewers, and verification specialists; select by visible role descriptions and task contracts rather than by exact names alone.
- Before delegating, identify the one immediate action that is both tightly coupled and blocking the coordinator's next step. Keep only that slice local. Delegate independent material implementation, exploration, validation, and verification sidecars. Do not label an entire phase or feature "critical path" to justify local execution; record the local slice and reason in the progress file.
- Merge tiny tasks into coherent delegated batches. Start with read-heavy parallelism when it can clarify decomposition, tests, logs, or risks without creating write conflicts.
- Keep parallel worker write scopes disjoint. If scopes overlap, serialize them or give one worker ownership. Keep delegation flat unless recursive delegation has a specific benefit and configured depth permits it.
- Choose the agent count that best fits the independent task decomposition and expected wall-clock or risk-reduction benefit. Avoid agents that create idle coordination, duplicate work, merge pressure, or token cost without a concrete return.
- Give each subagent a narrow task and bounded sufficient context to complete it independently: progress file path, owned scope, relevant files/modules, constraints, dependencies, acceptance criteria, validation commands, expected artifact, and a checkable stop condition.
- Assume coding workers edit in forked workspaces and return uploaded changes. Require each handback to identify the integration-state identity it received, its actual base revision and source fingerprint, and its intended delta. Lack of a visible patch in the coordinator workspace is expected while they run; review returned changes and reconcile them with the current authoritative integration state before integration.
- Treat each assigned write scope as owned by its worker until it completes, reports a blocker, fails terminally, asks for handback, violates scope or safety, or is confirmed stuck. While ownership is active, do not implement or patch the same scope locally.
- Do not interrupt or take over an active owned scope because the worker is slow, still analyzing, or has not produced a visible patch. Use coordinator time for non-overlapping work. Before any non-emergency handback or takeover, request objective status; if it shows active reasoning, an active command, or new evidence, preserve ownership and continue waiting without a coordinator-imposed time limit.
- Treat a worker as confirmed stuck only when it reports that it cannot proceed, enters a terminal error state, or repeated objective status checks show no active operation and no new action or evidence after a direct request to continue. Time alone never confirms that a worker is stuck.
- Treat a job-level timeout as terminal only when the worker or tool reports it, or when an explicit user, task, or worker-contract deadline expires with no active operation or forward progress. A coordinator wait timeout is never a job-level timeout.
- Prefer an explicit bounded prompt. Use `fork_context` only when supported and when material thread history cannot be summarized safely; do not rely on a context fork as a substitute for the progress path, owned scope, acceptance criteria, validation, and stop condition.
- Decide the current required verification portfolio from concrete risks, not phase size alone, and record each risk-to-assignment mapping before spawning reviewers. If a required assignment is retired, preserve the reason, evidence, risk disposition, and replacement when applicable in `Progress Log`. For ordinary low-risk phases, existing tests, builds, lint, reproducible checks, and coordinator review may provide the acceptance gate without a delegated verifier.
- Run required verification assignments in parallel with one another and with non-dependent work when safe. Serialize them before a dependent phase only when proceeding without all required verdicts would be unsafe.
- Never use the executor as any verifier of its own work. Use strict verification for high-risk surfaces and pragmatic or sampled verification for reports, prototypes, decision-support work, and repetitive low-risk edits after one representative strict check passes.
- Add or update tests only when changed behavior needs automated coverage to prove correctness or the request explicitly requires tests.
- Set a retry budget per phase, usually one retry before escalating or changing strategy.

## Execution Loop

At the start of each activity, read the progress file, reconcile every active agent ID with exactly one assignment, and choose the largest coherent pending batch that can complete safely. Apply the section boundaries prospectively while updating it; do not add new historical content to snapshot sections even when legacy content remains. Do not reuse an agent whose recorded assignment differs from the work now being delegated. If the run resumed in a different or uncertain runtime, visible role metadata changed, or an unresolved assignment changed materially, mark the affected current `Agent Selection` rows `Refresh Required` and refresh them before spawning those assignments. Leave legacy rows from previously `Accepted` phases inert; do not refresh, reorder, or remove them without an explicit cleanup request.

For each batch:

1. Begin the coordinator-local blocking slice identified under `Delegation And Batching`, if one exists. Spawn workers or explorers for independent material sidecars in the same round.
2. While subagents run, perform meaningful non-overlapping work. Do not redo an owned scope locally.
3. Call the wait tool only at a dependency barrier where the next critical action requires a subagent result and no productive non-overlapping work remains. Use a long wait window at that barrier. A wait timeout, long analysis, or lack of a visible coordinator-workspace patch is not a job-level timeout and is not a takeover condition; if the dependency still blocks progress and the worker remains active, continue waiting.
4. When an executor returns, review its uploaded changes and record its delegated integration-state identity, actual base revision and source fingerprint, intended delta, files changed, artifacts, commands, assumptions, blockers, and evidence before integration.
5. If a worker meets a terminal handback condition defined under `Delegation And Batching`, record the evidence, handback reason, returned workspace state, and ownership change in `Progress Log` before re-delegating or executing that scope locally. Re-delegation uses a fresh replacement instance bound to the same assignment.
6. Before freezing or integrating a candidate, enforce `Forward-Only Integration`: compare its recorded integration-state identity with the complete current authoritative state, port a stale candidate's intended delta onto the current state, classify every changed path, and prove preservation of affected `Accepted` guarantees. Block on any unresolved provenance or regression.
7. Keep the phase `Done` while running or delegating all required pre-acceptance integration validation against a frozen cumulative candidate. Complete any validation that reviewers require as evidence before spawning them; independent validation may run alongside reviews when safe.
8. Spawn every assignment in the phase's current required general or specialist verification portfolio from the recorded risk decomposition, in parallel when safe; otherwise use coordinator acceptance backed by existing validation.
9. If integration validation or any required verification assignment fails, return the phase to `Pending` or `In Progress` and record the failed gate, revision, and reason in `Progress Log`. Keep corrections in the existing implementation assignment only while its task type, primary deliverable, material ownership scope, and acceptance boundary remain stable; otherwise create a new implementation assignment with a fresh best-fit worker and an explicit dependency on the rejection. The coordinator may make only a small immediate integration correction after worker ownership has ended, and must record why local execution is appropriate.
10. Mark the phase `Accepted` only after its `Done When` criteria, required integration validation, coordinator gates, and every assignment in the current required verification portfolio pass against the same final frozen candidate and authoritative integration-state identity. Record the aggregated decision in `Progress Log` before dependent work consumes it.
11. Keep a `Done` executor available only through its same-assignment acceptance or retry decision. Close agents after their assignment is accepted, superseded, terminally failed, cancelled, or abandoned and their evidence is integrated; never retain them for later assignments.
12. Create checkpoint commits only when the user requested them or applicable project instructions require them. Let the user's checkpoint policy determine whether one commit combines changes from multiple phases; never split or reparent solely for phase purity, and never include unrelated user changes.
13. Update `Current State`, `Agent Selection`, `Execution Plan`, `Progress Log`, `Next Actions`, blockers, risks, agent lifecycle, and any requested checkpoint evidence.
14. Continue through later gates in the same activity when results are available and doing so reduces overhead. Stop only when waiting, user input, unresolved blockers, or a meaningful checkpoint makes continuation inefficient or unsafe.

Do not poll or wait by reflex. Ask for status only when there is evidence of a blocker, loop, external-input requirement, or a possible terminal handback condition. Apply the ownership and takeover criteria from `Delegation And Batching`.

## Completion

Finish only when all completion gates pass:

- Goal is defined and ready to mark complete.
- Source request, objective, scope, success definition, inventory, assumptions, risks, and current execution plan are captured.
- Required material phases are completed and accepted through their recorded coordinator or independent-verifier acceptance gates; independent work was delegated when it provided real time or risk benefit.
- Every `Execution Plan` phase is `Accepted` or `Not Applicable`; `Done` still awaits acceptance and cannot satisfy completion.
- `Agent Selection` contains no row for a newly `Accepted` phase, has one resolved row for every remaining non-terminal required assignment, contains no `Pending` or `Refresh Required` decisions, or is explicitly `Not Applicable` when no such assignment remains; every retired assignment is accounted for in `Progress Log`. Legacy rows from phases accepted before this rule may remain inert and do not block completion.
- `Next Actions` is `None`.
- Required validation passed, or validation gaps are documented and accepted.
- For repository-backed work, the final artifact is the cumulative current integration state, its complete identity is recorded, and the forward-only integration preflight passed without unclassified or retired-assignment content.
- Any user-requested or project-required checkpoint commits were created or documented with skip/failure reasons.
- Residual risks and any reliable final accounting are recorded in `Progress Log` or `Blockers And Risks`.
- Every assignment-bound subagent is closed after its assignment reaches an accepted or other terminal lifecycle state and its evidence is integrated; none remains available for a later assignment.

Mark the goal complete only after the objective is genuinely achieved. Record final accounting in the progress file when reliable timing or usage data is available; do not estimate unavailable values.

Final responses should synthesize the outcome, not replay agent activity. Mention decomposition only when it explains verification, risk, deferred work, or blockers. When relevant, include changed files, validation performed, completed activities, unresolved risks, blockers, next actions, and the progress file path. Do not claim success if validation failed or was not run.
